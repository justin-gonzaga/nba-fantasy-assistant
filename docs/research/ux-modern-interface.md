Access date for all entries: **2026-10-03** (noted per-row if a different date applies).
Method: WebSearch to locate the primary/official page, then WebFetch (direct, or via the

### Apple Human Interface Guidelines (HIG)

| ID | Status | Claim | Source | Confidence |
|---|---|---|---|---|
| UX-01 | Verified | Sidebars need "a large amount of vertical and horizontal space"; below that, use a more compact control such as a tab bar. Use a **split view** (sidebar + list + detail) when the data hierarchy is **deeper than two levels**; a plain sidebar is for ≤2 levels. Don't hide the sidebar by default — "avoid hiding the sidebar by default to ensure that it remains discoverable." Let people toggle it to reclaim room for detail. Prefer SF-Symbols-style vector icons over bitmaps; default icon tint follows the app/system accent, fixed colour only to clarify meaning, used sparingly. | [Sidebars — Apple HIG](https://developer.apple.com/design/human-interface-guidelines/sidebars) | High |
| UX-02 | Verified | Typography minimums by platform: iOS/iPadOS default **17pt**, minimum **11pt**; macOS default **13pt**, minimum **10pt**. Minimize the number of typefaces even in a custom UI — mixing too many "obscures hierarchy." Build hierarchy from weight + size + colour together, not size alone. Always pair a material with a *vibrant* (system-adjusted) colour, not a flat grey — flat greys on glass under-contrast. Give every chart mark a default accessibility label; write labels with real values, not vague terms ("high/low"). | [Charts — Apple HIG](https://developer.apple.com/design/human-interface-guidelines/charts) | High |
| UX-05 | Verified | Layout: decide layout from **size classes** (compact/regular × width/height), **not** device type or orientation directly. ### Nielsen Norman Group (NN/g)

| ID | Status | Claim | Source | Confidence |
|---|---|---|---|---|
| UX-12 | Verified | **Progressive disclosure**: show only primary/frequent features first; reveal secondary/advanced ones on request. Improves learnability, efficiency, and error rate for novices *and* saves experts from scanning irrelevant options — "users understand a system better when you help them prioritize features." **Risk**: designs with **more than two disclosure levels** typically have usability problems; misjudging what's "primary" forces repeated trips to the secondary layer, defeating the purpose. | [Progressive Disclosure — NN/g](https://www.nngroup.com/articles/progressive-disclosure/) | High |
| UX-13 | Verified | **F-shaped scanning**: users scan in an F-pattern (horizontal sweep top, shorter sweep below, vertical scan down the left) when content is unformatted and they're skimming, not reading fully — confirmed as "alive and well" on desktop and mobile in NN/g's own recent eye-tracking work. Content on the right side of an F-scanned layout risks being skipped. Counter-measures: put the key fact first in each paragraph/line; front-load headings (first 1–2 words should carry the meaning); use real subheadings, bold key terms, bullets; visually group related content with borders/background; cut unnecessary content entirely. | [F-Shaped Pattern of Reading on the Web — NN/g](https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content/) | High |
| UX-14 | Verified | **Data tables**: design to support 4 user tasks — find/filter records, compare rows, view-edit-add a single row, act on records. Freeze header row **and** header column when a table is bigger than the viewport. Use borders, zebra striping, and hover-row-highlight together to help users track position across wide rows. Default column order should reflect importance, with related columns adjacent. First column should be a human-readable identifier, not a raw/"mystery meat" ID. Column show/hide and reordering should be easy, with a clear indicator of which columns are currently hidden. Filters must be quick, discoverable, and "transparent" (the user can tell exactly what's being filtered). | [Data Tables: Overview — NN/g](https://www.nngroup.com/articles/data-tables/) | High |
| UX-15 | Verified | **Preattentive processing for dashboards**: length and 2D position are processed fastest/most accurately by the visual system → prefer **bar charts** (length) and **line/scatter** (2D position) for quantitative comparison. Area, angle and colour are noticed quickly but judged *less accurately* — avoid pie/donut/gauge charts for precise comparison; use colour/shape only for *categorical* grouping, never to encode magnitude; avoid 3D, which distorts position/length judgements. | [Dashboards: Making Charts and Graphs Easier to Understand — NN/g](https://www.nngroup.com/articles/dashboards-preattentive/) | High |
| UX-16 | Verified | **8 guidelines for complex applications** (directly applicable to a decision-support tool): (1) let people act/explore with visible, reversible feedback rather than long blind action sequences; (2) teach faster paths in-context (tooltips/hints) rather than relying on external docs; (3) non-linear, escapable workflows — no forced linear funnels; (4) let users annotate/record their own reasoning so they can resume analysis later; (5) support export/handoff to other tools people already use; (6) **reduce clutter via staged disclosure, not reduced capability** — show advanced settings only once the relevant primary choice is made; (7) let people see supporting detail (tooltips, expandable rows) without leaving the primary view; (8) make the important thing salient by **removing** competing decoration, not by adding emphasis on top of clutter. | [8 Design Guidelines for Complex Applications — NN/g](https://www.nngroup.com/articles/complex-application-design/) | High |
| UX-17 | Verified | **Empty states** (3 guidelines): (1) never show a truly blank space — always state the system status explicitly (e.g. "No records for the selected date range") so the user isn't unsure if it's loading, broken, or genuinely empty; (2) use the empty state as an in-context teaching moment ("Star your favourites to list them here") — this works better than a forced upfront tutorial; (3) give a direct action/link from the empty state into the task that would populate it, not just a description of what's possible. | [Designing Empty States in Complex Applications — NN/g](https://www.nngroup.com/articles/empty-state-interface-design/) | High |
| UX-18 | Verified | **Skeleton screens vs. spinners vs. progress bars**: skeleton screens (structural placeholders) improve *perceived* performance and user satisfaction specifically for loads in roughly the **400ms–3s** range by showing the page "assemble" rather than ambiguous motion. NN/g's general wait-time guidance: show nothing for waits "about 1s" or less is tolerated without an indicator at all; use a plain spinner/indicator for waits of roughly 2–10s; use a percent-done/progress indicator for anything longer. (The "reduces bounce rate 9–20%" figure circulating in SEO blogs could not be traced to an NN/g primary page and is **not** used here.) | [Skeleton Screens vs. Progress Bars vs. Spinners — NN/g](https://www.nngroup.com/videos/skeleton-screens-vs-progress-bars-vs-spinners/) | Medium — the 400ms–3s window and task-duration bands are corroborated by the NN/g video title/description via search snippet; I was not able to open full video transcript text, only the indexed summary. The qualitative ordering (skeleton for page loads; spinner short; progress bar long) is High confidence; exact millisecond cutoffs are Medium. |

## 2. Data-dense patterns (synthesis across UX-06…UX-20, plus direct typography source below)

| ID | Status | Claim | Source | Confidence |
|---|---|---|---|---|
| UX-21 | Verified | **Tabular numerals / number alignment**: numbers should use fixed-width (tabular) digit forms so columns align vertically (Courtside §2 already specifies this — corroborated). Numeric columns are **right-aligned** (or decimal-aligned) because people compare magnitude digit-by-digit from the ones place outward; text columns are **left-aligned**; headers align with their column's data; **never centre-align** a data column. Round every value in a column to the same number of decimal places. | [Alignment in Tables — Max Masnick](https://masnick.org/projects/datatips/guidelines/alignment-in-tables/) (independent practitioner reference corroborating a widely-held typographic convention) | Medium-High — the underlying convention (right-align numbers, left-align text) is extremely well established and is also implied by Apple's tabular-figure guidance (UX-02); the specific secondary source is a practitioner page, not a standards body. |
| UX-22 | — (synthesis, not a new source) | **Sticky headers + density modes**, combining UX-09 and UX-14: freeze the header row (and ideally the identifying first column) on any table taller than the viewport; offer a density toggle (comfortable default, compact for power users scanning many rows) rather than picking one row height for everyone. | Derived from UX-09 (M3 density-as-choice) + UX-14 (NN/g frozen headers) | High (both parent claims High) |
| UX-23 | — (synthesis) | **Zebra striping vs. rules**: NN/g (UX-14) recommends borders, zebra striping, *and* hover-highlight together, rather than treating them as alternatives — each helps a different task (zebra = track a row while scanning horizontally; hover = confirm current row; border/rule = separate header from body or mark a sub-total). Courtside currently uses hairline rules (`--line`) with no zebra; given the owner's "barebones" feedback, consider a very low-contrast zebra (e.g. `surface` vs `surface-2` at low opacity) **on data tables only**, not on list/card UI, to avoid breaking the existing calm aesthetic. | Derived from UX-14 | Medium (the specific recommendation to add zebra to Courtside is this report's synthesis, not a sourced claim) |
| UX-24 | Unverified (no primary standards body defines this numerically; widely-practiced convention) | **Inline micro-visualizations** — sparklines (small trend-over-time line, no axes), bullet charts (actual-vs-target horizontal bar), and diverging bars (bar growing left or right from a central zero, used for z-scores/percentile deltas) are a standard way to pack a trend or a comparison into a table cell or stat-card without a full chart. No authoritative source gave numeric sizing; treat sizing as an implementation choice, built from Courtside's existing spacing/colour tokens (e.g. diverging bar: `win`/`lose` tokens either side of a centred zero line, bar length ∝ z-score magnitude, capped at a sensible max so one outlier doesn't flatten the rest). This directly matches UX-15's "length/position first" preattentive-processing rule. | General practice (Edward Tufte's sparkline concept, widely adopted; not independently re-verified here) | Low-Medium — pattern is extremely common and consistent with UX-04/UX-15, but no primary spec was opened for sparkline/bullet-chart sizing specifically. |
| UX-25 | — (synthesis from UX-04 + UX-15 + Baseball Savant pattern, §3) | **Uncertainty/range display**: an interval bar (min–median–max or P10–P50–P90) is a natural extension of a bullet chart — draw the full range as a thin track, the point estimate as a filled segment or tick, label only the endpoints and the estimate (not every gridline), per Apple's "concise axis labels, familiar tick steps" (UX-04) and NN/g's "length/position, not colour-only" rule (UX-15). Never use colour alone to signal "wide range = risky" — pair with the width of the bar itself (an inherently perceptual, non-colour-dependent signal) plus a text label ("±4.2" or "wide range"). | Synthesis | Medium |
| UX-26 | — (synthesis from UX-10) | **Badge/chip count discipline**: M3 caps a badge's own label at 4 characters (UX-10); by extension, cap the number of *distinct* badges/chips shown per row/card at a small number (recommend **≤3** visible before a "+N more" or an overflow affordance) so badges stay scannable and don't compete with the primary number — this specific "≤3" count is this report's recommendation, not a numbered rule from M3 (M3 doesn't state a max chip *count* per row in the pages opened). | Synthesis, informed by UX-10 and UX-13 (F-pattern/scanning load) | Low-Medium |

## Proposed additions to `design-language.md`

1. **Desktop shell breakpoints** — adopt M3's breakpoints as Courtside's own (UX-06): Compact <600px (phone), Medium 600–839px, Expanded 840–1199px (tablet landscape / small desktop — **sidebar appears here**), Large 1200–1599px, Extra-large ≥1600px. Below 600px: tab bar (existing). ≥840px: persistent left sidebar nav replaces the tab bar; ≥1200px: content column gets a max-width (see #2) and a right detail panel becomes available.
2. **Max content width on desktop** — cap the main content column at **1200px** (data-table pages) in the Expanded/Large range, with extra horizontal space going to the sidebar and an optional detail panel, not to the table itself; above 1600px (Extra-large), re-evaluate rather than let tables stretch arbitrarily wide (UX-31).
3. **Sidebar spec** — width **240–320px**, collapsible, never hidden by default (UX-01); 3–7 top-level destinations (UX-07); icon + label, same icon set as the existing tab bar.
4. **Split-view / detail-panel rule** — once a page's data is >2 levels deep (e.g. list → player → stat-category), add a right-hand detail panel instead of full navigation; this is exactly the player-detail case the owner flagged (UX-01, UX-31).
5. **Home page anatomy** — in order: current recommendation/action (1 line) → freshness timestamp (state explicitly, never implied) → 3–5 primary actions as cards, not a menu wall → compact roster/league summary cards → link to full tables. No dense tables above the fold (UX-32).
6. **Signed-out landing anatomy** — hero (outcome-led headline + problem subhead + one primary CTA) → one short "how it works"/demo section → an honest proof section (sample screenshot, build notes, repo link — never fabricated testimonials/usage stats for a project with no real users) (UX-33).
7. **Stat table spec** — numeric columns right-aligned with tabular figures (already Courtside; reinforced by UX-02/UX-21); text columns left-aligned; same decimal places down a column; sticky header row (+ sticky first/identifier column on wide tables) past viewport height (UX-14, UX-22); a density toggle (comfortable default / compact) rather than one fixed row height (UX-09); add a very low-contrast zebra stripe on data tables specifically (not on cards/lists) given the "barebones" feedback (UX-23); first column is a human-readable name, never a raw ID (UX-14).
8. **Player-detail page anatomy** — order: identity header (photo, name, team/position, 1-line achievement/role badges) → compact recent-performance summary cards (not a full table yet) → **one signature indicator visual** (percentile/diverging bars — see #9) that answers "is this player good, and at what" in one glance → progressively deeper tables/tabs below (UX-27, UX-28, UX-30). This is the direct fix for "the player detail's indicators and stats" feedback.
9. **Indicator/percentile visual spec** — render each indicator (role, certainty, consistency, punt-fit, range, age, etc.) as a **horizontal bar on a shared scale** (length/position, not colour-coded cells — UX-15, UX-04): diverging bars from a centred zero for z-score-like signals (`win`/`lose` tokens either side); a single-direction bar 0→100 for percentile-like signals, with a consistent colour scale across all indicators on a page (not one hue per metric) so the shape of the column, not individual colours, carries the "good/bad" read, matching Baseball Savant's pattern (UX-27). Uncertainty/ranges render as a thin track + filled point/segment, labelled only at the estimate and the two endpoints (UX-04, UX-25) — never colour-only (UX-19, WCAG 1.4.1).
10. **Badge/chip discipline** — cap visible badges/chips per row or card at **≤3**, with overflow behind a "+N" affordance (UX-10, UX-26); badge text ≤4 characters where it's a count.
11. **Density modes** — introduce a page-level density toggle (comfortable/compact) for any page with a data table of >~15 rows, defaulting to comfortable (UX-09).
12. **Empty/skeleton states** — extend WEB-016: every empty state must (a) state status in words, never a blank box, (b) teach ("Star players to see them here"), (c) link directly into the action that fills it (UX-17); skeletons (not spinners) for the typical 400ms–3s table/card load; spinner only for genuinely indeterminate/longer waits (UX-18).
13. **Visual QA checklist additions** (for screenshot reviews, append to Courtside §7): [ ] desktop ≥1280px shows sidebar + content + (if applicable) detail panel, content column not stretched past ~1200px; [ ] every data table: numeric right-aligned/tabular, sticky header, zebra visible but subtle, density is comfortable by default; [ ] player detail shows identity → summary cards → one indicator-bar visual → tables, in that order; [ ] every indicator/range uses a bar (length), not colour-only; [ ] badges per card ≤3 + overflow; [ ] all interactive targets ≥24×24px (WCAG 2.5.8, UX-20) in addition to the existing ≥44px touch rule; [ ] focus ring never fully obscured by a sticky header (WCAG 2.4.11, UX-20).
